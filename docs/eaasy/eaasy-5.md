# 书摘：Google 系统架构解密：构建安全可靠的系统 —— 设计系统

一个内置可靠性和安全性功能，同时具备稳健性的框架，这是一个双赢的方案：开发人员采用该框架的原因是它简化了开发流程并将常见杂务自动化，使得他们的日常工作更轻松、更高效。该框架提供了一个通用的功能界面，安全工程师和网站可靠性工程师都可以在其中构建新功能，从而为提高自动化程度和加快项目整体速度创造机会。

有一个普遍的现象，特别是在较小的团队中，那就是倾向于将安全性和可靠性问题往后搁置。（他们会说：“当我们拥有一定的客户后，就会加强安全性和考虑扩展问题。”）为了“速度”，团队通常认为在设计初期牺牲安全性和可靠性能够提升速度，他们担心花费时间思考和解决这些问题会减缓开发速度，并给他们的第一个发布周期带来不可接受的延迟。

最小特权原则是指，用户应该只拥有完成任务所需的最低权限，不管访问是来自人还是来自系统。在调试、停机响应或者执行紧急响应任务时，你和你的同事临时手工执行的命令中，有多少是如果打错一个字母或者复制粘贴失误就可能导致停机的？

这句直接说中了前不久的一级故障。拥有管理权限，想删除当前目录所有的内容，想使用相对路径，但是忘了加 . 符号 导致所有目录被删除，花了大半天去恢复。

安全性和可靠性的权衡：测试环境。
与能真实反映生产环境的测试环境不同，时间和成本方面的考虑会诱导你在生产环境中使用特殊的测试账号，使变更不会影响到实际用户。此策略在某些情况下是有效的，但涉及审计和 ACL 时，可能会使情况变得复杂。
前期构建一个尽可能还原的测试环境，只付出一次成本，后续的开发和更新的负担都会更小。

本书中对系统易理解性的定义是，有相关技术背景的人员能够准确、自信地解释以下两点：  
◆ 系统运行时的行为；  
◆ 系统的不变性约束条件，包括安全性和可用性。


以下是系统期望的安全性和可靠性属性的一些样例。  
◆ 只有通过身份认证和相应授权的用户才能访问系统的持久化数据存储。  
◆ 根据系统的审计策略，对于系统中持久化数据存储中敏感数据的所有操作都记录在审计日志中。  
◆ 从系统边界外接收的所有值，在传递到容易出现注入漏洞的 API（如 SQL 查询 API，或者构造 HTML 内容的 API）之前都应经过适当的验证或者编码。  
◆ 系统后端接收的查询数量与系统前端接收的查询数量之间成比例。  
◆ 如果系统后端在预定时间内未能响应，则系统的前端应优雅降级，比如使用近似的答案来响应。  
◆ 当任何组件的负载超过其处理能力时，为降低连锁故障的风险，该组件应呈现服务过载错误，而不是崩溃。  
◆ 一个系统只能从一组特定系统接收 RPC 请求，并且将 RPC 发送到一组特定系统。

频繁发布、容器化和微服务等设计策略使得主动改进和缓解紧急情况变得更加容易，而分层结构则可以减少暴露面并方便管理。深思熟虑的设计和进度文档，这两者都要着眼于变更。

在实现优雅降级时，无论是什么原因触发了问题，确定和记录系统降级的级别都很重要。此信息对于诊断和调试很有用。报告实际的降低负载或限流（无论是自行实施还是定向）都有助于评估全局运行状况和容量，并检测错误或攻击。

维护一种拥抱并关注良好代码健康度的团队文化很重要。领导层可以从多方面支持这种文化。例如，定期为团队安排 Fixit 活动周。在此期间，开发人员将重点从添加新功能转向改善代码健康以及修复未解决的错误。可以通过奖金或其他形式的表彰来推动团队内对代码健康度的持续贡献。

永远不要将重构和功能变更混在同一次向代码仓库的提交中。重构变更通常很重要并且难于理解。如果此次提交同时包含了功能变更，那么开发人员或审查者很可能会遗漏一些缺陷。

无论是对编写还是使用的人来说，框架都有助于提高研发效能并代码更容易理解。除此以外，编写安全、可靠代码的策略还包括力求简洁、选择正确的工具、使用强类型而不是原始类型，以及不断清理代码库。

只有经常使用，调试技巧才能保持最新。熟悉相关的工具和日志，记住我们在此提供的建议，有助于加快调查速度。定期做调试还有助于将流程中常见和烦琐的部分编写成脚本，例如自动检查日志。为了更好地掌握调试技巧（或保持敏锐度），需要经常练习并保留在调试过程中编写的代码。
